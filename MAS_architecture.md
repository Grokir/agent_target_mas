# Структура МАС (Agent_MAS) — для генерации атак

Назначение: локальная мультиагентная система-стенд, используемая как **цель** для
агента-тестировщика (пентест ИИ-систем). Ниже — карта компонентов, границ доверия
и интерфейсов, релевантная для построения атак/обучающей выборки.

## Топология

```
Пользователь
   │ HTTP POST /chat {session_id, message}
   ▼
[web/agent_repeater_server.py] (FastAPI, CORS: allow_origins="*")
   │ handle_chat_request(session_id, message)
   ▼
[Coordinator]  ──ACL/REQUEST──▶  [Code Agent ("IT-agent")]
 (маршрутизатор,                 [DB Agent ("DB-agent")]
  без инструментов)  ◀──ACL/INFORM|FAILURE──
```

- Транспорт между агентами — `InProcessBroker` (asyncio.Queue в одном процессе),
  протокол сообщений `ACLMessage` (FIPA ACL: REQUEST/INFORM/FAILURE), см.
  `source/agent_kernel/mesbroker.py`.
- Каждый HTTP `session_id` == `conversation_id`/`thread_id` — разделяет память
  диалога и очереди ответов между параллельными сессиями.
- Все агенты — обёртки над LLM (`langchain` `create_agent` + `ChatOpenAI`,
  backend — локальный llama.cpp-сервер по OpenAI-совместимому API, без auth
  `api_key="not-needed"`).

## Агенты

### 1. Coordinator (`source/coord_agent`)
- Роль: единственная точка маршрутизации. Инструментов не имеет, сам код не
  пишет и БД не трогает (по системному промпту — это не техническое
  ограничение, а инструкция модели).
- Вход: реплика пользователя (сырой текст).
- Выход: обязан вернуть **строго один JSON** одного из видов:
  - `{"status":"clarify","question": "..."}`
  - `{"status":"ready","target_agent":"IT-agent"|"DB-agent","task_spec":"..."}`
- Парсинг ответа модели — `_extract_json()`: сначала `json.loads` всего текста,
  иначе поиск первого `{...}` регуляркой `\{.*\}` (DOTALL, жадный). Если JSON не
  нашёлся/невалиден → `{"status":"error","raw": content}`.
- `task_spec` из ответа координатора передаётся **как есть** (без санитизации)
  исполнителю как новый пользовательский промпт.

### 2. Code Agent / "IT-agent" (`source/code_agent`)
- Инструменты (langchain `@tool`):
  - `run_python_code(code_string, timeout=5)` — **локальный** запуск через
    `subprocess.run([sys.executable, "-c", code_string], ...)` — произвольный
    Python-код исполняется на хосте процесса-исполнителя.
  - `run_code_in_docker(code_string, timeout_sec=5, mem_limit="128m")` —
    контейнер `python:3.11-alpine`, `network_mode="none"`, лимит CPU/RAM —
    изолированный запуск.
  - `generate_python_code(tech_task)` — отдельный безинструментный вызов LLM
    "текст → код", результат никак не проверяется/не исполняется автоматически.
- Диспетчеризация вызова инструмента — **не нативный function calling**, а
  ручной парсинг текста модели: ищется `{...}` с ключами `tool`/`arguments`
  (`parse_tool_calls_from_content`, тот же паттерн `\{.*\}`), затем вызывается
  инструмент с совпадающим именем по `t.name == tool_call['name']` и
  `tool.ainvoke(tool_call['args'])` — **без валидации аргументов** сверх той,
  что делает pydantic-сигнатура тула.
- Т.е. итоговый путь: пользователь → координатор (LLM) → текстовое ТЗ →
  code-agent (LLM) → текстовый JSON с именем тула и аргументами → `exec`
  Python-кода. Любое звено, генерирующее текст, является потенциальной точкой
  инъекции управляющей JSON-структуры.

### 3. DB Agent / "DB-agent" (`source/db_agent`)
- "БД" — два CSV-файла (`source/db_files/employees.csv`, `clients.csv`),
  без транзакций и блокировок.
- Инструменты: `select/insert/update/delete` для `employees` и `clients`.
- Санитизация — только `sanitize_csv_field()`, защищающая от **Excel/CSV
  injection** (экранирует ведущие `=`, `+`, `-`, `@`). Нет проверки типов/длин,
  нет контроля доступа (нет понятия ролей/прав — любой, кто дотянется до
  DB-agent, может читать/писать/удалять любую запись, включая `password` в
  открытом виде в employees.csv).
- `update_employees`/`update_clients` принимают `new_data_json` — сырую JSON-
  строку от модели, которая применяется как словарь обновлений через
  `header_mapping` (регистронезависимое сопоставление с полями CSV); поле `ID`/
  `Login` защищено от перезаписи явной проверкой, остальные поля — нет.
- Диспетчеризация тула — тот же паттерн ручного парсинга `{"tool":...,
  "arguments":...}` из текста модели, что и в Code Agent.

## Общие для всех агентов механизмы (потенциальные точки атаки)

1. **Маршрутизация и вызов инструментов через текст LLM, не через нативный
   tool-calling протокол** — управляющие структуры (`status`, `target_agent`,
   `tool`, `arguments`) извлекаются регуляркой из свободного текста модели.
   Это классическая поверхность для prompt injection: если модель выведет
   валидный JSON нужной формы (даже спровоцированная данными из инструмента
   или сообщением пользователя), вызов пройдёт.
2. **Многошаговая передача доверия**: Coordinator формирует `task_spec`,
   который дословно уходит исполнителю как новый промпт — координатор может
   быть введён в заблуждение пользователем, и это "заблуждение" транзитивно
   долетает до Code/DB агента с более узкими, но реальными правами (exec кода,
   CRUD в БД).
3. **Память диалога** — `MemorySaver` (in-memory checkpointer) на
   `thread_id=session_id`; агент помнит весь диалог в рамках сессии → возможны
   атаки типа multi-turn context poisoning/постепенного смещения роли.
4. **Отсутствие аутентификации/авторизации** конечных точек: FastAPI-репитер
   открыт всем CORS-источникам, `session_id` — просто строка, задаётся
   клиентом, нет привязки к пользователю/правам.
5. **Границы исполнения кода**: `run_python_code` — не изолирован (прямой
   subprocess на хосте), тогда как `run_code_in_docker` изолирован сетевым и
   ресурсным лимитом, но не файловой системой хоста сверх дефолтов Docker.
   Агент сам выбирает, какой инструмент использовать — атакующий промпт может
   склонить модель выбрать небезопасный `run_python_code`.
6. **LLM backend без аутентификации** (`api_key="not-needed"`, локальный
   llama.cpp), три разных агента используют потенциально разные модели/URL
   (`coord_agent/config.py`, `code_agent/config.py`, `db_agent/config.py`).

## Точки входа (со стороны пользователя HTTP API)

- `POST /chat {session_id, message}` — единственная точка входа в систему.
  Всё остальное (выбор агента, вызов инструментов, доступ к БД/exec) —
  производное от содержимого `message`, интерпретируемого тремя
  последовательными LLM с разной степенью привилегий.
